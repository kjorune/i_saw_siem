# 테이렌 기업 프로젝트 OT 요약 및 분석 주제 추정

## 문서 해석 기준

- 이 문서는 「테이렌 기업프로젝트 OT자료」 15쪽의 내용을 요약한 것이다.
- **자료에서 명시한 내용**과 **자료를 토대로 한 추론**을 구분하였다.
- 아래의 확률은 통계모델로 산출한 확률이 아니라, OT 자료의 반복 강조 정도, 구현 범위, 예상 필드, 검증 방법 및 산출물과의 정합성을 기준으로 평가한 **주제 채택 가능성 추정치**다. 각 주제는 서로 배타적이지 않으므로 합계가 100%일 필요가 없다.
- 이전 대화에서 언급된 `하루 약 50GB의 로그`와 `사고 인지에 6개월~1년 소요`는 이 PDF에는 기재되어 있지 않다. 테이렌 관계자의 별도 설명이나 인터뷰 정보라면 별도 근거로 관리해야 한다.

## 1. 테이렌 개요

### 회사와 제품

테이렌은 클라우드, 서버, 애플리케이션 및 보안 솔루션에서 발생하는 로그를 하나의 환경에서 수집·검색·분석하는 **Cloud SIEM**을 개발한다. OT 자료에서 제시한 주요 기능은 다음과 같다. `[OT p.2~3]`

- 로그 통합 관리: 다양한 보안 로그의 수집·저장·검색
- 위협 탐지: 알려진 위협과 이상행동 탐지
- 공격 흐름 분석: 사용자·자산·IP 사이의 관계 및 상관관계 분석
- 보안 규정 관리: 증적과 컴플라이언스 지원
- 분석 결과 제공: 대시보드, 알림 및 상세 분석

전체 SIEM 과정은 `로그 발생 → 로그 수집 → 보안 분석 → 상관관계 분석 → 분석 결과`로 구성된다. 이번 기업 프로젝트는 이 중 **보안 분석을 중심으로 사용자·자산별 이상도를 계산하고 위험 우선순위와 근거를 제공하는 영역**을 담당한다. `[OT p.3~4]`

## 2. 기업 프로젝트의 명시적 목표

프로젝트 공식 주제는 다음과 같다.

> **보안 로그 기반 이상탐지 및 위험 스코어링 시스템 개발**

입력된 보안 로그에서 사용자 또는 자산별 정상 행동 기준선을 만들고, 현재 행동이 기준선에서 얼마나 벗어났는지 계산한 뒤, 복수의 이상 신호를 결합하여 0~100점의 위험점수와 산정 근거를 제공하는 것이 목표다. 쉽게 말하면 **“누가 가장 이상하게 행동하고 있는지 자동으로 정리하는 시스템”**이다. `[OT p.1, p.4]`

### 프로젝트가 해결하려는 문제

| 문제 | OT 자료의 설명 | 분석적 의미 |
|---|---|---|
| 로그 규모 | 하루에도 다수 이벤트가 발생해 전체 로그만으로 우선순위를 정하기 어려움 | 모든 이벤트를 사람이 보는 대신 위험 대상을 순위화해야 함 |
| 사용자별 정상 차이 | 같은 행동도 사용자마다 평소 패턴이 다름 | 고정 임계치보다 개인별 기준선이 필요함 |
| 단일 이벤트의 한계 | 야간 로그인 하나만으로 침해를 판단하기 어려움 | 인증·IP·자산·데이터 접근 등 복수 신호를 함께 봐야 함 |

`야간 로그인 5회`라는 동일 행동도 평소 야간 접속이 없던 사용자에게는 강한 이상이지만, 평소 4회 수행하던 사용자에게는 정상 범위일 수 있다는 예시가 제시된다. `[OT p.5]`

## 3. 예상 데이터와 분석 단위

OpenSearch에 저장된 보안 이벤트 로그를 이용하며, 예상 주요 필드는 다음과 같다. 실제 분석에서는 예시 데이터에 존재하는 필드를 먼저 확인한 뒤 사용할 지표를 선정하도록 명시되어 있다. `[OT p.6]`

| 필드 | 의미 | 예상 활용 |
|---|---|---|
| `timestamp` | 이벤트 발생 시각 | 야간·비업무시간 행동, 기간별 집계, 기준선 |
| `user_id` | 사용자 식별자 | 사용자별 행동 기준선과 위험 순위 |
| `asset_id` | 시스템·자산 식별자 | 신규 자산 접근과 자산별 확장 분석 |
| `src_ip` | 접속 IP | 신규 IP 및 접속 출발지 변화 |
| `event_type` | 이벤트 유형 | 인증·DB·다운로드·권한 이벤트 구분 |
| `action` | 수행 행동 | 사용자·자산별 행위량 집계 |
| `result` | 성공·실패 | 로그인 실패 및 성공 패턴 분석 |
| `resource` | 접근 대상 | 신규 서버·DB·리소스 접근 탐지 |
| `bytes` | 데이터 처리량 | 다운로드·전송량 급증 탐지 |

### 분석 단위

- **기본 구현 권장:** 사용자 단위 분석
- **확장 기능:** 자산 단위 분석

따라서 첫 구현은 `User → 행동 패턴 → 이상도 → 위험점수`가 될 가능성이 높다. 자산 단위의 `Asset → 접근 패턴 → 이상도 → 위험점수`는 데이터 품질과 개발 일정에 따라 추가하는 범위다. `[OT p.6]`

## 4. 제시된 분석 방법론

분석 파이프라인은 다음 여섯 단계다. `[OT p.7]`

```text
보안 로그
  → 특징 집계
  → 사용자별 기준선 생성
  → 현재 행동의 이상도 계산
  → 복수 신호의 가중 위험점수
  → 점수 산정 근거
  → 위험 대상 순위
```

### 기준선

최근 30일과 같은 과거 기간에서 사용자별 로그인 횟수, 야간 로그인, 로그인 실패, DB Query, 다운로드 용량의 평균적 행동 범위를 계산한다. 자료에서는 사용자별 정상 범위를 “평소 성적”에 비유한다. `[OT p.8]`

### 이상도

예시 방법은 Z-score다.

```text
z = (현재값 - 기준선 평균) / 기준선 표준편차
```

자료의 예시 구간은 `|z|<1 정상`, `1≤|z|<2 약한 변화`, `2≤|z|<3 이상징후`, `|z|≥3 강한 이상`이다. 다만 임계값은 실제 로그 분포를 보고 조정하도록 되어 있다. `[OT p.9]`

### 위험점수와 설명

복수 지표의 이상점수에 중요도 가중치를 적용해 0~100점으로 통합한다. 가중치는 정답이 아니며 팀별 기준과 실험을 통해 조정한다. 최종 결과에는 단순 점수뿐 아니라 야간 로그인, 신규 IP, DB Query 증가, 신규 DB 접근처럼 **어떤 신호가 몇 점을 기여했는지** 표시한다. `[OT p.11~12]`

## 5. OT 자료에서 제시한 후보 이상 신호

| 영역 | 후보 지표 | 판단 방식 |
|---|---|---|
| 접속 시간 | 야간 로그인 횟수 | 평소 접속시간 대비 증가 |
| 인증 | 로그인 실패 횟수 | 평소보다 짧은 시간에 반복 실패 |
| 네트워크 | 신규 Source IP | 과거 기준기간에 없던 IP |
| 자산 | 신규 자산 접근 | 기존에 접근하지 않던 서버·DB |
| 데이터 | DB Query·다운로드 | 평소보다 활동량·처리량 급증 |
| 권한 | 관리자 기능 사용 | 평소보다 권한 관련 이벤트 증가 |

팀별로 제공 로그를 확인하고 **최소 3개의 분석지표를 선정**하게 되어 있으며, 모든 지표를 구현할 필요는 없다고 명시되어 있다. `[OT p.10]`

## 6. 구현 및 검증 범위

### 기술 구성

| 구성요소 | 역할 |
|---|---|
| OpenSearch | 보안 로그 조회 |
| Python | 전처리·집계·통계 계산 |
| 위험 분석 모듈 | 기준선·이상도·위험점수 계산 |
| Streamlit 또는 Jupyter | 위험 순위와 상세 근거 조회 |
| GitHub·Notion | 코드 및 프로젝트 문서 관리 |

UI를 화려하게 만드는 것은 핵심이 아니며, 위험 순위와 산정 근거를 확인할 수 있는 수준이면 충분하다. `[OT p.13]`

### 검증 시나리오

- 정상 사용자: 평소와 유사한 로그 → 낮은 위험점수
- 단일 이상행동: 야간 로그인만 증가 → 일부 점수 증가
- 복합 이상행동: 야간 로그인 + 신규 IP + DB 접근 증가 → 높은 위험점수

### 6주 일정과 산출물

`데이터 이해 → 기준선 설계 → 이상도 계산 → 위험점수 → 화면 구현 → 검증·발표` 순으로 진행한다. 최종 산출물은 소스코드, 결과 화면, 분석설계서, 검증 결과 및 발표자료다. 완료 기준은 **보안 로그 입력 후 사용자별 위험점수를 계산하고 위험 순위와 주요 근거를 확인할 수 있는 상태**다. `[OT p.14]`

## 7. 분석 프로젝트 주제 채택 가능성 추정

### 80% 이상 후보

| 순위 | 추정 주제 | 채택 가능성 | 판단 근거 |
|---:|---|---:|---|
| 1 | **사용자별 정상 행동 기준선 기반 복합 이상탐지 및 설명 가능한 위험 스코어링** | **99%** | 프로젝트 제목, 범위, 방법론, 결과 화면 및 완료 기준이 모두 이 주제를 직접 명시함 |
| 2 | **야간 로그인·로그인 실패·신규 IP를 결합한 계정 이상행동 탐지** | **96%** | 사용자 단위 구현이 권장되고, 인증 관련 세 지표가 여러 예시와 검증 시나리오에서 반복 사용됨 |
| 3 | **복수 이상 신호의 가중 결합을 통한 위험 사용자 우선순위화** | **95%** | 단일 이벤트의 한계를 해결하는 것이 핵심 문제이며 0~100 위험점수·순위 생성이 필수 산출물임 |
| 4 | **DB Query 및 다운로드 급증을 이용한 비정상 데이터 접근 탐지** | **93%** | `resource`, `bytes`가 예상 필드로 제시되고 기준선·점수 설명 예시에 DB Query와 다운로드가 포함됨 |
| 5 | **신규 IP·신규 서버·신규 DB 접근을 이용한 관계 변화 탐지** | **89%** | 신규 Source IP와 신규 자산 접근이 공식 후보 지표이며 사용자·자산·IP 관계분석이 제품 기능으로 제시됨 |
| 6 | **관리자 기능 사용 증가를 이용한 권한행위 이상탐지** | **83%** | 권한 이벤트가 공식 후보 지표지만 인증·DB 접근보다 예시와 검증에서 강조되는 빈도는 낮음 |

### 가장 가능성이 높은 최종 주제 형태

위 후보들은 별개의 프로젝트라기보다 하나의 최종 프로젝트 안에서 결합될 가능성이 크다. 가장 현실적인 최종 제목은 다음과 같다.

> **사용자별 정상 행동 기준선과 인증·IP·자산·데이터 접근 이상 신호를 결합한 설명 가능한 위험 스코어링 및 우선순위화 시스템**

구현 범위를 6주에 맞춰 축소한다면 다음 세 지표 조합이 가장 유력하다.

1. 야간 로그인 또는 로그인 실패 증가
2. 신규 Source IP 또는 신규 자산 접근
3. DB Query 또는 다운로드량 급증

이 세 영역을 선정하면 OT 자료의 검증 시나리오인 `야간 로그인 + 신규 IP + DB 접근 증가`를 그대로 구현할 수 있고, 시간·인증·네트워크·자산·데이터 행동을 함께 설명할 수 있다.

## 8. 예시 데이터 수령 후 확정해야 할 사항

현재 추정은 예상 필드를 기준으로 한다. 실제 주제는 다음 조건을 확인한 후 확정해야 한다.

- `user_id`가 안정적으로 존재하며 사용자별 기간 집계가 가능한가?
- 최소 30일 이상의 정상 기준선 구간이 있는가?
- `timestamp`의 타임존과 시스템별 시간 동기화가 확인되는가?
- 로그인 실패, DB Query, 다운로드, 관리자 기능을 구분할 `event_type` 또는 `action`이 있는가?
- 신규 IP·신규 자산을 판단할 `src_ip`, `asset_id`, `resource`가 충분히 채워져 있는가?
- `bytes`는 실제 다운로드·전송량인가, 단순 이벤트 크기인가?
- 정상·단일 이상·복합 이상을 검증할 라벨이나 시나리오 데이터가 있는가?
- 사용자 수와 사용자별 관측일수가 기준선을 만들 만큼 충분한가?
- 표준편차가 0인 사용자와 신규 사용자를 어떻게 처리할 것인가?
- 위험점수 가중치의 근거를 전문가 판단, 데이터 분포 또는 검증결과 중 무엇으로 정할 것인가?

이 조건 중 핵심 필드가 누락되면 관련 지표의 채택 가능성은 크게 달라진다. 예를 들어 `bytes`가 없으면 다운로드 급증 분석을 제외하고, `asset_id`가 불완전하면 신규 자산 접근보다 인증행동 중심으로 범위를 좁히는 것이 적절하다.
