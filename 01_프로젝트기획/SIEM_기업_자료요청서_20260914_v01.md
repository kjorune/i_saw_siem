# SIEM 이상행동 조기탐지 프로젝트 기업 자료 요청서

## 1. 요청 목적

본 프로젝트는 기업의 보안 로그를 기반으로 다음 기능을 구현하는 것을 목표로 합니다.

- 사용자·IP·자산별 정상 행동 기준선(Baseline) 생성
- 로그인·접속·자원 접근 과정의 이상행동 탐지
- Credential Stuffing 및 Account Takeover 의심행동 조기탐지
- 개별 이상신호를 하나의 Incident로 연결하는 Event Correlation
- 공격 진행단계(Attack Stage) 추정
- 관련 IP·사용자·Host·Resource 추적
- Dynamic Risk Score 산출
- 보안담당자가 즉시 확인할 수 있는 탐지 근거 및 대응 권고 제공
- 공격 시작부터 최초 탐지까지의 시간(MTTD) 단축 가능성 검증

프로젝트 기간 내에 초기 데이터 구조 확인 이후 바로 분석·개발에 착수할 수 있도록 아래 자료 제공을 요청드립니다.

# 2. 우선 제공을 요청드리는 핵심 자료

아래 자료는 프로젝트 착수 시 가장 먼저 필요한 항목입니다.

| 우선순위 | 요청 자료 | 세부 내용 | 권장 범위/기간 | 권장 형식 | 활용 목적 |
|---:|---|---|---|---|---|
| 1 | 인증 로그 | 로그인 성공/실패, 사용자 ID, Source IP, 대상 시스템, 실패 사유, 세션 정보 | 가능하면 2~4주 이상 | CSV, JSON, NDJSON | 계정탈취·Credential Stuffing 탐지 |
| 2 | 접근/행위 로그 | 로그인 후 사용자 행동, 서비스·페이지·서버·DB·Resource 접근 | 인증 로그와 동일 기간 | CSV, JSON, NDJSON | 로그인 성공 이후 행동 변화 분석 |
| 3 | 로그 필드 정의서 | 컬럼명, 의미, 타입, 예시값, NULL 의미, 코드값 정의 | 전체 | XLSX, CSV, 문서 | 로그 정확한 해석 및 공통 Schema 설계 |
| 4 | 사용자/계정 메타데이터 | user_id, 계정 유형, 부서/Role, 관리자 여부, 서비스 계정 여부 | 현재 기준 | CSV, XLSX | 사용자 행동 기준선 및 오탐 감소 |
| 5 | IP/자산 메타데이터 | 내부·외부 IP 구분, Host, 서버, DB, 서비스, 자산 중요도 | 현재 기준 | CSV, XLSX | IP/계정/자산 추적 및 Context Risk |
| 6 | 정상 기간 로그 | 비교적 사고가 없었던 기간의 실제 로그 | 가능하면 2~4주 이상 | CSV, JSON, NDJSON | 정상 행동 Baseline 구축 |
| 7 | 실제 사고·이상행동 사례 | 과거 Incident 전후 로그 또는 비식별화 로그 | 사고 전후 수시간~수일 | CSV, JSON, NDJSON | 실제 공격 탐지 성능 및 MTTD 검증 |
| 8 | 현재 탐지 Rule/정책 | 현재 적용 Rule, threshold, severity 기준 | 현재 운영 기준 | YAML, JSON, XLSX, 문서 | 기존 방식과 제안 모델 비교 |
| 9 | 로그 수집 주기/지연 정보 | 이벤트 발생 후 SIEM 적재까지 시간, 수집 주기 | 운영 기준 | 문서, 인터뷰 | Near Real-Time 설계 및 MTTD 산출 |
| 10 | OpenSearch/SIEM 연동 구조 | index, mapping, timestamp, 샘플 document, API 여부 | 현재 운영 기준 | JSON, 문서, OpenAPI | 실제 기업 환경과의 연동 가능성 검토 |

# 3. 로그 데이터 요청 상세

## 3.1 인증 로그

가능한 경우 아래 필드가 포함된 로그를 요청드립니다.

| 필드 | 설명 | 필수도 |
|---|---|---|
| `timestamp` | 이벤트 발생 시각 | 필수 |
| `user_id` | 사용자/계정 식별자 | 필수 |
| `src_ip` | 접속 Source IP | 필수 |
| `dst_ip` | 대상 서버/서비스 IP | 권장 |
| `result` | 로그인 성공/실패 | 필수 |
| `failure_reason` | 실패 사유 | 권장 |
| `service` | 로그인 대상 서비스 | 권장 |
| `host_id` | 대상 Host 식별자 | 권장 |
| `session_id` | 세션 식별자 | 있으면 매우 유용 |
| `device_id` | Device/Endpoint 식별자 | 선택 |
| `user_agent` | 브라우저/Agent 정보 | 선택 |
| `geo_country` | 접속 국가 | 선택 |
| `asn` | ASN/통신사업자 정보 | 선택 |

### 활용 예시

- 동일 IP의 단시간 대량 로그인 탐지
- 하나의 IP가 여러 계정을 공격하는 패턴 탐지
- 사용자별 신규 Source IP 탐지
- 평소와 다른 시간대 로그인 탐지
- 로그인 실패 급증 탐지
- 실패 후 성공하는 Credential Stuffing 성공 의심 패턴 탐지

---

## 3.2 사용자 접근/행위 로그

로그인 성공 후 계정탈취 여부를 판단하기 위해 아래와 같은 행동 로그가 중요합니다.

| 필드 | 설명 | 필수도 |
|---|---|---|
| `timestamp` | 행동 발생 시각 | 필수 |
| `user_id` | 사용자 식별자 | 필수 |
| `src_ip` | 행동 발생 Source IP | 권장 |
| `host_id` | 접근 Host | 권장 |
| `resource` | 접근한 시스템/페이지/DB/Resource | 필수에 가까움 |
| `action` | 조회, 수정, 다운로드 등 | 권장 |
| `event_type` | 이벤트 유형 | 권장 |
| `result` | 성공/실패 | 선택 |
| `session_id` | 세션 식별자 | 있으면 매우 유용 |
| `request_id` | 요청 추적 ID | 선택 |

### 활용 예시

- 로그인 성공 직후 평소 접근하지 않던 Resource 접근
- 신규 DB/서버 접근
- 민감 자원 접근
- 비정상적인 조회·다운로드 흐름 분석
- Event Correlation 및 Incident 생성

---

## 3.3 네트워크 로그

가능한 경우 방화벽, Proxy, NetFlow 등 네트워크 계층 로그도 요청드립니다.

| 필드 | 설명 | 필수도 |
|---|---|---|
| `timestamp` | 연결 시각 | 필수 |
| `src_ip` | Source IP | 필수 |
| `dst_ip` | Destination IP | 필수 |
| `src_port` | Source Port | 선택 |
| `dst_port` | Destination Port | 권장 |
| `protocol` | TCP/UDP 등 | 권장 |
| `bytes_in` | 유입 데이터량 | 권장 |
| `bytes_out` | 외부 전송량 | 권장 |
| `action` | Allow/Deny | 권장 |
| `session_id` | 세션 ID | 선택 |

### 활용 예시

- 공격 Source IP 추적
- 내부 Host 간 이동 추적
- 비정상 목적지 접근
- 평소 대비 외부 전송량 급증
- 데이터 반출 가능성 분석

---

## 3.4 DB/데이터 접근 로그

개인정보나 중요 데이터 접근 이후의 이상행동을 탐지하기 위해 가능하면 요청드립니다.

| 필드 | 설명 | 필수도 |
|---|---|---|
| `timestamp` | 접근 시각 | 필수 |
| `user_id` | 사용자 식별자 | 필수 |
| `db_name` | DB 식별자 | 권장 |
| `resource` | Table/Resource | 권장 |
| `query_count` | Query 수 | 있으면 매우 유용 |
| `rows_accessed` | 조회 Row 수 | 선택 |
| `bytes` | 조회/다운로드 크기 | 권장 |
| `action` | 조회/수정/다운로드 | 권장 |

### 활용 예시

- 평소 대비 DB Query 급증
- 신규 DB 접근
- 민감 Resource 접근
- 계정탈취 이후 데이터 조회 폭증
- Data Exfiltration Risk 평가

## 3.5 Host / Endpoint / 권한 관련 로그

# 4. 기준선(Baseline) 구축을 위한 메타데이터

## 4.1 사용자/계정 정보

실명, 이메일 등 직접식별정보는 필요하지 않습니다. 비식별화된 식별자만으로 분석 가능합니다.

| 요청 필드 | 활용 |
|---|---|
| `user_id` | 로그 연결 키 |
| `role` | 일반 사용자/개발자/관리자 등 행동 차이 반영 |
| `account_type` | 사람 계정/서비스 계정/배치 계정 구분 |
| `department` | Peer Group 기준선 가능 |
| `is_admin` | 관리자 계정 오탐 감소 |
| `active_status` | 휴면/퇴사/비활성 계정 구분 |

---

## 4.2 자산 정보

| 요청 필드 | 활용 |
|---|---|
| `host_id` | Host 추적 |
| `host_type` | PC, 서버, DB, Gateway 구분 |
| `resource_id` | 자산 연결 |
| `asset_type` | DB, API, 파일 서버 등 |
| `criticality` | 자산 중요도 |
| `contains_sensitive_data` | 민감정보 자산 여부 |
| `network_zone` | 내부망/DMZ/외부망 구분 |

가능하다면 중요도를 다음처럼 단순하게 제공해도 충분합니다.

- Critical
- High
- Medium
- Low

| 알려진 악성 IP 정보 | Threat Context 보조 |

# 5. 과거 사고·정탐·오탐 자료 요청

실제 탐지 성능을 검증하기 위해 매우 중요한 자료입니다.

## 5.1 과거 실제 Incident

가능하다면 아래 정보만 비식별화하여 제공해주셔도 분석에 큰 도움이 됩니다.

| 항목 | 설명 |
|---|---|
| Incident ID | 익명 ID 가능 |
| 공격 유형 | 계정탈취, Credential Stuffing 등 |
| 공격 시작 추정 시점 | MTTD 기준 |
| 기존 시스템 최초 탐지 시점 | 기존 MTTD 계산 |
| 실제 확인 시점 | 사후 발견 시간 |
| 관련 사용자 | 익명 user_id 가능 |
| 관련 IP | 마스킹 또는 가명처리 가능 |
| 관련 Host/Resource | 비식별 ID 가능 |
| 관련 로그 범위 | 사건 전후 로그 |

### 가장 유용한 형태

예를 들어 다음과 같이 제공받을 수 있습니다.

```text
incident_id: INC_001
attack_type: Account Takeover
attack_start: 2026-01-01 02:10
detected_at: 2026-01-01 03:20
confirmed_at: 2026-01-02 10:15
user_id: USER_001
src_ip: IP_001
affected_resource: RESOURCE_003
```

---

## 5.2 오탐 사례

가능한 한 많이 요청드립니다.

예:

- 야간근무자의 정상 심야 로그인
- 관리자 계정의 다수 Host 접속
- 배치 작업의 대량 Query
- 사내 VPN 사용으로 인한 신규 IP
- 정상 이벤트성 트래픽 급증
- 운영 점검으로 인한 관리자 권한 사용

오탐 사례는 본 프로젝트에서 **False Positive Rate를 줄이는 데 매우 중요**합니다.

---

## 5.3 미탐 사례

가능하다면 가장 우선적으로 요청드리고 싶은 자료입니다.

즉,

> 실제 공격이었으나 당시 SIEM/Rule에서는 경보가 발생하지 않았던 사례

입니다.

이 자료가 있으면 기존 탐지 체계와 본 프로젝트 모델을 직접 비교하여 다음을 검증할 수 있습니다.

- 기존 Rule이 놓친 공격을 탐지하는가
- 몇 분/몇 시간 먼저 발견할 수 있었는가
- 어떤 신호가 조기탐지에 기여했는가

# 6. 현재 보안 운영 관련 자료

## 6.1 현재 탐지 Rule

가능한 범위 내에서 아래 자료를 요청드립니다.

- 현재 로그인 이상탐지 Rule
- IP 관련 Rule
- 인증 실패 threshold
- 데이터 접근량 관련 Rule
- Alert Severity 결정기준
- Whitelist 기준
- Rule 예외조건

전체 Rule 공개가 어려운 경우 대표적인 Rule 일부만으로도 충분합니다.

---

## 6.2 현재 보안담당자의 조사 절차

Alert가 발생했을 때 담당자가 실제로 어떤 순서로 조사하는지 알고 싶습니다.

예:

```text
Alert 확인
→ 사용자 확인
→ Source IP 확인
→ 과거 로그인 기록 확인
→ 동일 IP 접근 계정 확인
→ 로그인 이후 행동 확인
→ 관련 Host 확인
→ DB/Resource 접근 확인
→ 공격 여부 판단
```

이 정보를 기반으로 Dashboard에서 자동으로 제공해야 할 Evidence를 설계할 수 있습니다.

# 7. 실시간 탐지 구현을 위한 시스템 정보

본 프로젝트는 가능한 한 빠른 탐지를 목표로 하기 때문에 아래 운영정보가 필요합니다.

| 요청사항 | 확인 내용 |
|---|---|
| 로그 발생→수집 지연 | 평균 몇 초/몇 분인지 |
| SIEM 적재 지연 | OpenSearch 등에 저장되기까지 시간 |
| 로그 수집 주기 | 실시간/1분/5분/배치 |
| Index 갱신 주기 | 검색 가능한 시점 |
| 평균 로그량 | 초/분/일 이벤트 건수 |
| Peak 로그량 | 공격 또는 피크 시 최대량 |
| 보존기간 | Baseline 학습 가능 기간 |
| 로그 순서 보장 여부 | 늦게 도착하는 로그 존재 여부 |

특히 `로그 생성 시각`과 `SIEM 적재 시각`이 둘 다 존재한다면 함께 제공을 요청드립니다.

이를 통해 다음을 구분할 수 있습니다.

- 데이터 수집 자체의 지연
- 탐지 모델 처리시간
- 전체 MTTD

# 8. OpenSearch / SIEM 연동 자료

현재 시스템과 직접 연동 가능한 PoC를 만들 수 있다면 아래 자료를 요청드립니다.

## OpenSearch 사용 시

- Index 목록
- 분석 대상 Index
- Index Mapping
- Timestamp field
- Sample document
- Query 예시
- 인증 방식
- 테스트용 Endpoint 여부
- Read-only 테스트 계정 제공 가능 여부

예:

# 10. 데이터 비식별화 관련 안내

본 프로젝트에서는 개인의 실명이나 직접식별정보가 필요하지 않습니다.

아래와 같이 가명화하여도 분석 가능합니다.

```text
hong_gildong
→ USER_001

server-production-customer-db
→ DB_001

실제 내부 IP
→ IP_001
```

단, 다음 관계는 유지되어야 합니다.

> 동일한 원래 값은 항상 동일한 가명 값으로 변환

예를 들어 동일 사용자는 모든 로그에서 동일한 `USER_001`로 유지되어야 Event Correlation이 가능합니다.

또한 IP를 가명화하는 경우에도 아래 특성은 가능하면 별도 필드로 유지해주시면 좋습니다.

- 내부/외부 IP 여부
- 동일 IP 여부
- VPN 여부
- Proxy/NAT 여부
- 국가/ASN 정보가 있는 경우 해당 값

# 11. 데이터 제공 시 유의사항


공격 순서를 분석하기 어렵습니다.

```text
10:01 LOGIN_FAIL
10:02 LOGIN_FAIL
10:03 LOGIN_FAIL
10:05 LOGIN_SUCCESS
10:08 RESOURCE_ACCESS
10:12 DB_QUERY
```

이 정보가 있어야 Event Correlation과 Attack Stage 분석이 가능합니다.

# 12. 1차/2차 제공 권장 방식

프로젝트 기간이 짧기 때문에 자료를 한 번에 모두 준비하실 필요는 없습니다.

## 1차 제공 — 프로젝트 시작 즉시

다음 자료를 먼저 요청드립니다.

1. 로그 샘플 1~2일치
2. 로그 필드 정의서
3. Event Code 정의
4. 사용자/자산/IP 메타데이터 샘플
5. OpenSearch sample document 또는 mapping
6. 기업에서 우선적으로 탐지하고 싶은 공격 유형

이 자료로 데이터 구조와 개발 방향을 확정합니다.

## 2차 제공 — 구조 확인 후

1. 정상 기간 로그 2~4주
2. 실제 사고/이상 사례
3. 오탐/미탐 사례
4. 현재 탐지 Rule
5. 전체 메타데이터
6. 운영환경 정보

를 요청드립니다.

이 방식이 불필요한 대용량 데이터 전달을 줄이고 프로젝트 초반 시행착오를 줄일 수 있습니다.

# 13. 기업 담당자께 확인드리고 싶은 질문

## 운영 관련

10. 대응 시 가장 많이 참고하는 정보는 무엇인가요?

## 시스템 관련

11. 로그는 평균적으로 이벤트 발생 후 몇 초/몇 분 이내에 SIEM에 들어오나요?
12. OpenSearch에서 직접 조회 가능한 테스트 환경이 있나요?
13. API 또는 Read-only 계정 제공이 가능한가요?
14. 동일 Session을 식별하는 ID가 존재하나요?
15. user/IP/host/resource를 연결할 수 있는 공통 키가 있나요?

16. 기업 측에서 프로젝트 성공을 판단할 가장 중요한 기준은 무엇인가요?

18. 몇 분 이내 탐지되면 실무적으로 의미가 있다고 보시나요?

# 14. 본 프로젝트에서 측정하고자 하는 주요 성능지표

가능한 데이터가 제공되는 경우 아래 지표를 측정하고자 합니다.

| 지표 | 의미 |
|---|---|
| MTTD | 공격 시작부터 최초 탐지까지 걸린 시간 |
| Detection Recall | 실제 공격 중 탐지한 비율 |
| Precision | 발생한 경보 중 실제 공격 비율 |
| False Positive Rate | 정상 행동을 공격으로 잘못 판단한 비율 |
| Correlation Accuracy | 관련 이벤트를 동일 Incident로 연결한 정확도 |
| Attack Stage Detection | 공격 진행단계 식별 성능 |
| Trace Coverage | 관련 IP/User/Host/Resource 추적 범위 |
| Explainability Coverage | 탐지 결과에 근거를 제공할 수 있는 비율 |

특히 기존 탐지 방식과 비교가 가능한 경우,

```text
기존 Rule 기반 탐지
vs.
제안하는 Baseline + Anomaly + Correlation 기반 탐지
```

형태로 탐지율, 오탐률, MTTD를 비교하고자 합니다.

# 17. 요청사항 정리

프로젝트 착수 시에는 우선 **로그 샘플과 Schema를 먼저 제공받아 구조를 확인한 뒤**, 실제 개발에 필요한 전체 데이터 범위를 확정하는 방식이 가장 효율적입니다.

기업의 보안·개인정보 정책상 제공하기 어려운 데이터는 실명 등 직접식별정보를 제거하거나 가명처리하여 제공해주셔도 됩니다.

다만 프로젝트의 핵심 기능인 사용자 행동 기준선, IP 기반 추적, Event Correlation을 구현하기 위해서는 **동일 사용자·IP·Host·Resource가 로그 간에 일관되게 연결될 수 있는 식별관계**가 유지되어야 합니다.

본 요청사항은 가능한 모든 자료를 반드시 요구하는 목록이 아니라, 기업에서 제공 가능한 범위를 확인하고 해당 범위 내에서 가장 실용적인 탐지 모델을 설계하기 위한 체크리스트입니다.
