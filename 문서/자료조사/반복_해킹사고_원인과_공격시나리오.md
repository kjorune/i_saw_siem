# 반복된 해킹 사고 원인 유형과 현실적 공격 시나리오

## 결론

최근 사고에서 반복된 핵심 문제는 새로운 해킹 기술 자체보다 **탈취되거나 회수되지 않은 정상 자격증명을 신뢰하고, 인증 이후의 권한 사용과 데이터 접근량을 감시하지 못한 것**이다. 반복 원인은 `신원·자격증명 → 권한·인가 → 외부 노출 → 내부 확산 → 데이터·API → 탐지·대응 → 증거·거버넌스`의 일곱 유형으로 정리할 수 있다. 네 전문가 관점을 종합했을 때 가장 현실성이 높은 단일 시나리오는 **탈취된 직원·협력사 계정 또는 API 키로 정상 인증한 뒤 고객정보 API를 저속·분산 조회하여 반출하는 공격**이다.

> 원인을 분석할 때는 `직접 침투 원인`, `공격을 허용한 관리 실패`, `피해를 확대한 조건`, `탐지·조사를 어렵게 한 문제`를 구분한다. 최초 침투 경로가 확인되지 않은 사고는 추정을 확정 원인처럼 표현하지 않는다.

## 1. 반복 원인 유형

| 유형 | 반복된 핵심 문제 | 피해로 이어지는 과정 | 중요하게 수집할 데이터 | 우선 방지·탐지 대책 |
|---|---|---|---|---|
| 1. 신원·자격증명 통제 실패 | 유출·재사용 비밀번호, 장기 미회전 API·서명키, 퇴직자·협력사 계정 미회수 | 공격자가 유효한 계정·키를 사용하므로 정상 요청처럼 보임 | 계정 상태, 입·퇴사/직무변경, 키 발급·사용·회전·폐기, 토큰·세션, MFA, IP·단말 | 피싱 저항형 MFA, 계정·키 자동 회수, 단기 자격증명, 비밀관리 저장소, 키 자동 회전 |

| 3. 외부 노출·초기 침투 관리 실패 | 인터넷 노출 서버·관리 포트, 미패치 취약점, 피싱·정보탈취 악성코드 | 서버 또는 단말을 발판으로 계정·토큰을 획득 | 외부 노출 자산, 포트·서비스, 취약점·패치, 이메일 URL·첨부, 프로세스 계보, C2 통신 | 공격표면 관리, 신속 패치, 관리면 비공개, EDR·메일 보안, 자격증명 접근 탐지 |
| 4. 내부 확산·피해 제한 실패 | 망 세분화 부족, 관리자 계정 재사용, 광범위한 동서 통신, 백업망 공유 | 한 시스템의 침해가 다수 서버·백업·업무중단으로 확대 | 내부 연결, 원격관리 프로토콜, 관리자 로그인, 자산 중요도, 백업 접근·삭제 | 마이크로세그멘테이션, PAM, 관리자 계정 분리, 백업 격리·불변화, 동서 트래픽 감시 |
| 5. 데이터·API 보호 실패 | API 과다 응답, 순차 ID 조회, 호출량 제한 부재, 암호화 데이터와 복호화 수단 동시 노출 | 정상 API만 반복 호출해도 대규모 정보 수집 가능 | API 주체·세션, 요청률, 고유 객체 수, 응답 필드·바이트, 순차 ID, 오류 후 재시도 | 최소 응답, 속도·총량·고유 객체 제한, 스키마 보안검사, 암호키 분리, DLP |

| 7. 로그·증거·거버넌스 실패 | 감사로그 누락·짧은 보존, 로그 삭제, 사고 후 재설치, 책임자·소유자 불명확 | 최초 침투 시점과 피해 범위를 규명하지 못해 대응·통지가 지연 | 로그 수집 상태, 감사정책 변경, EDR 중지, 시간 동기화, 증거 해시·인계, 자산·키 소유자 | 중앙 불변 로그, 보존정책, 증거보존 절차, 수집 중단 자체 경고, CPO/SOC/서비스 책임 명확화 |

### 원인 간 연결 구조

```text
자격증명 탈취·외부 노출
        ↓
정상 인증 또는 초기 침투
        ↓
과도한 권한·약한 API 인가
        ↓
대량 조회·내부 확산·자료 반출
        ↓
행위 탐지 실패·대응 지연
        ↓
로그 부족으로 원인·피해 범위 규명 곤란
```

## 2. 네 전문가의 토의 결과

| 전문가 관점 | 중점 의견 | 시나리오 선정에 반영한 판단 |
|---|---|---|
| 침해사고·포렌식 | 직접 침투 원인과 피해 확대·조사 실패 요인을 분리해야 함 | 특정 사고의 미확정 침투 경로를 단정하지 않고, 여러 사고에서 반복 확인된 통제 실패를 사용 |
| SOC·SIEM 탐지 | 정상 인증 뒤의 최초 접근·조회량·전송량을 한 흐름으로 묶어야 함 | 단일 IP 이상보다 `신원+권한+행위량+데이터 영향` 상관분석이 가능한 시나리오를 선택 |
| 기업 보안책임자 | 실제 적용 가능한 우선순위와 업무중단 위험이 중요함 | 제로데이보다 빈도가 높고 기본통제로 위험을 실질적으로 낮출 수 있는 자격증명 악용을 선택 |
| 공격경로·레드팀 | 공격자는 비용이 낮고 정상 기능을 악용해 탐지를 피할 수 있는 경로를 선호함 | 유효 계정·정상 API·저속 분산 조회를 결합한 공격이 재현성과 은닉성이 가장 높다고 판단 |

**합의 결론:** 가장 현실적인 시나리오는 고도화된 신종 악성코드보다 **탈취된 정상 자격증명으로 허용된 API를 악용하는 개인정보 유출**이다. 웹·클라우드·SaaS 환경에 공통 적용되고, 계정·키 관리 실패, 최소권한 미흡, 대량조회 통제 부재, 탐지 지연이라는 반복 이슈를 하나의 공격 흐름으로 설명할 수 있다.

## 3. 선정 시나리오와 방지 대책 — A4 반쪽 분량

### 시나리오: 탈취한 정상 자격증명을 이용한 개인정보 API 저속 반출

#### 참고 사고와 반영 범위

이 시나리오는 한 사고의 공격 과정을 그대로 재현한 것이 아니라, 아래 사고에서 공개적으로 확인된 요소를 결합한 **복합 가상 시나리오**다. 따라서 `저속·분산 호출`, `피싱·정보탈취 악성코드`, `외부 저장소 반출` 등은 현실적인 공격 가능성을 설명하기 위해 추가한 가정이며, 해당 기업의 조사 결과로 확정된 사실이 아니다.

| 시나리오 구성 요소 | 참고한 사고 | 공개자료에서 확인된 내용 | 시나리오에서 추가한 가정 |
|---|---|---|---|
| 탈취·잔존 자격증명을 이용한 정상 인증 | **쿠팡 개인정보 유출 사고** | 개인정보위가 인증 서명키 관리 및 접근통제 소홀을 주요 안전조치 문제로 판단 | 협력사 계정과 세션 토큰이 피싱·인포스틸러로 탈취되는 구체적 최초 침투 방법 |
| 유출 비밀번호를 이용한 계정 접근과 탐지 지연 | **GS리테일 GS SHOP·GS25 사고** | 크리덴셜 스터핑으로 로그인에 성공했고, 대규모 로그인 시도·실패율 급증을 장기간 인지하지 못함. 일부 공격 IP가 두 서비스에서 공통 사용됨 | 직원·협력사 계정을 공격 대상으로 설정하고 야간 신규 단말 로그인을 결합한 부분 |
| 정상 API를 통한 정보 수집 및 API 응답·키 관리 문제 | **‘모두의 창업’ 정보유출 사고** | 공개 보도상 일부 API에 비공개 정보가 포함됐고 외부 수집 과정에서 노출됐으며, 복호화 관련 정보 노출이 문제로 지적됨 | 고객 ID를 순차 변경하고 여러 IP에서 저속 호출하도록 구성한 회피 방법 |
| 인증서·비인간 신원과 내부 접근통제 문제 | **KT 침해사고** | 정부 조사에서 인증서 관리, 내부망 접속제한, 비인가 장비 탐지 문제가 지적됨 | API 공격의 직접 경로로 사용한 것이 아니라, 계정 외 인증서·키도 동일하게 관리해야 한다는 통제 관점만 반영 |
| 개인정보 DB 비인가 접근 시 발생 가능한 영향 | **티빙 개인정보 유출 사고** | 개인정보위 조사 착수 자료에서 개인정보 DB 비인가 접근 및 다수 개인정보 항목의 유출 정황을 확인 | 공개된 조사 착수 자료만으로는 구체적 침투·반출 방법이 확인되지 않아 공격 방법의 근거로 사용하지 않음 |

**주요 참고축:** 공격 시작과 인증 우회는 쿠팡·GS리테일, API를 통한 데이터 노출 가능성은 ‘모두의 창업’, 비인간 자격증명 관리와 내부 통제는 KT 사고를 주로 참고했다. 티빙 사고는 개인정보 DB 침해 시 영향 범위를 설명하는 보조 사례로만 사용했다.

공격자는 피싱이나 정보탈취 악성코드로 협력사 직원의 계정과 세션 토큰을 획득한다. 이 계정은 업무 변경 후에도 고객정보 조회 권한이 남아 있고 피싱 저항형 MFA가 적용되지 않았다. 공격자는 야간에 신규 클라우드 IP에서 로그인하지만 유효한 토큰을 사용하므로 인증은 정상 처리된다. 이후 고객지원 화면과 API를 시험 호출해 고객 ID 규칙과 응답 항목을 파악한다. 탐지를 피하기 위해 한 번에 대량 다운로드하지 않고 여러 IP와 시간대로 나눠 고객 ID를 순차 변경하며 개인정보를 조회한다. 계정별 호출 횟수만 보면 임계치를 넘지 않지만, 평소보다 조회한 고유 고객 수와 응답 바이트는 크게 증가한다. 객체 단위 인가와 대량조회 제한이 없어 공격은 수일간 지속되고, 결과는 정상 HTTPS를 통해 외부 저장소로 반출된다. 기업이 로그인 성공만 신뢰하고 신규 단말, 직무 외 최초 접근, 고유 고객 수, 개인정보 필드와 전송량을 연결하지 못하면 외부 신고가 들어올 때까지 사고를 인지하지 못할 수 있다.

방어는 계정 보호에만 머물러서는 안 된다. 우선 입·퇴사와 직무 변경을 IAM에 연동해 계정·세션·API 키를 즉시 회수하고, 피싱 저항형 MFA와 단기 토큰을 적용한다. 고객정보 시스템은 직무 기반 최소권한과 객체 단위 인가를 적용하며, 계정별 요청률뿐 아니라 시간당 고유 고객 수·민감 필드 수·응답 바이트에 한도를 둔다. 대량조회와 내보내기에는 재인증과 승인을 요구한다. 탐지는 `신규 IP·단말 → 직무 외 시스템 최초 접근 → 순차 ID 조회 → 고유 고객 수·응답량 급증 → 외부 전송`을 동일 사용자·세션으로 묶어 경고해야 한다. 위험도가 높으면 세션 폐기, 토큰·키 비활성화, API 일시 제한을 단계적으로 수행한다. 인증·IAM·API Gateway·DB·프록시·DLP 로그는 시간 동기화 후 변경 불가능한 중앙 저장소에 보존하고, 로그 수집 중단이나 감사정책 변경도 별도 고위험 경고로 처리한다.

## 4. 권고 탐지식과 운영 지표

### 우선 경고 조합

```text
신규 IP/단말 또는 비정상 시간대
+ 유효하지만 오래되거나 장기 미사용한 계정·키
+ 직무 범위 밖 자산 또는 최초 API 접근
+ 조회한 고유 고객 수·민감 필드·응답 바이트 급증
+ 순차 ID 또는 여러 IP를 사용한 분산 호출
+ 외부 저장소 전송 또는 로그·감사정책 변경
= 최우선 조사 대상
```

### 권고 운영 지표

- 퇴직·직무변경 후 계정·키 회수까지 걸린 시간
- 장기 미사용 및 장기 미회전 키의 비율
- 개인정보 API의 객체 단위 인가 적용률
- 대량조회 통제와 추가 승인 적용률
- 이상행위 발생부터 탐지·차단까지의 시간
