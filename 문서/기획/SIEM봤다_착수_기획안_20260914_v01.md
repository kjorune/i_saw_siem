# SIEM봤다! 킥오프 기획안 예시

## 1. 프로젝트 주제

### 프로젝트명

**사용자 행동 로그 기반 보안 이상행동 탐지 및 위험도 산정**

### 한 줄 설명

로그인, 파일, USB, HTTP 등의 사용자 행동 로그를 분석하여 개인별 정상 행동 기준선을 만들고, 기준에서 벗어난 행동을 탐지해 위험 사용자와 판단 근거를 제시한다.

### 분석 흐름

```text
로그 데이터 확인
→ 사용자·시간 기준 데이터 통합
→ 정상 행동 기준선 생성
→ 이상행동 탐지
→ 위험 점수 산출
→ 위험 사용자와 행동 흐름 시각화
```

## 2. 주제 선정 이유

### 문제 상황

기업에는 로그인, 파일 접근, USB 연결, 웹 사용 등 많은 로그가 쌓이지만 개별 로그만으로는 실제 위험 행동인지 판단하기 어렵다.

예를 들어 야간 로그인 하나만으로 공격을 단정할 수 없지만 다음 행동이 연속으로 발생하면 위험 가능성이 커진다.

```text
비정상 시간 로그인
→ 평소와 다른 PC 사용
→ 대량 파일 접근
→ USB 연결
→ 파일 이동
```

### 선정 이유

- 단일 로그가 아닌 사용자 행동 흐름을 분석할 수 있음
- 기업 보안 환경에서 실제 활용 가능한 주제임
- 사용자별 정상 패턴을 기준으로 이상행동을 설명할 수 있음
- Z-score를 이용하면 위험 점수의 근거를 제시할 수 있음
- 향후 Isolation Forest 등 머신러닝 모델과 비교할 수 있음
- 현재 확보한 로그 데이터로 최소 기능을 구현할 수 있음

## 3. 목표와 범위

### 의사결정 주체

## 4. 데이터와 그레인 이해

그레인은 **한 행이 무엇을 의미하는지**를 뜻한다.

| 파일 | 예상 그레인 | 주요 확인 항목 |
|---|---|---|
| `logon.csv` | 사용자 1명의 로그인·로그아웃 이벤트 1건 | 사용자, PC, 활동, 시간 |
| `device.csv` | USB 등 장치 연결·해제 이벤트 1건 | 사용자, PC, 장치 활동, 시간 |
| `file.csv` | 파일 관련 행동 1건 | 사용자, PC, 파일, 활동, 시간 |
| `http.csv` | 웹 접속 이벤트 1건 | 사용자, URL 또는 도메인, 시간 |
| `email.csv` | 이메일 송수신 이벤트 1건 | 발신자, 수신자, 첨부파일, 시간 |
| `psychometric.csv` | 사용자 1명의 심리 측정 결과 | 사용자, 성향 지표 |
| `LDAP/` | 사용자 또는 조직 기준정보 1건 | 사용자, 부서, 직급 등 |
| `license.txt` | 데이터 사용 조건 | 분석·배포 가능 범위 |

### 통합 분석 그레인 잠정안

**사용자 × 일 단위**를 기본 분석 단위로 사용한다.

| 사용자 | 날짜 | 로그인 실패 | 야간 접속 | 파일 활동 | USB 사용 | HTTP 활동 |
|---|---:|---:|---:|---:|---:|---:|
| U001 | 2026-09-01 | 8 | 3 | 120 | 1 | 45 |

시간 단위 탐지가 필요하면 `사용자 × 시간` 또는 `사용자 × 세션`으로 세분화한다.

## 5. 도구와 기술 스택

| 영역 | 도구·기술 | 선정 이유 |
|---|---|---|
| 데이터 탐색 | Python, Pandas | 팀이 접근하기 쉽고 CSV 분석에 적합 |
| 대용량 처리 후보 | Polars | Pandas 처리 속도가 부족할 때 대안으로 사용 |
| 데이터 저장·조회 | CSV, SQLite 또는 DuckDB | 샘플 분석과 SQL 검증이 쉬움 |
| 데이터 정규화 | Python | 시간·단위·컬럼 처리 자동화 |
| 이상 탐지 | Z-score | 설명 가능하고 지표별 이상 정도를 제시할 수 있음 |
| 비교 모델 | Isolation Forest | 여러 지표의 종합적인 이상 패턴 비교 가능 |
| 시각화 | Matplotlib, Seaborn, Plotly | 탐색용·발표용 그래프 제작 가능 |
| 협업 | GitHub, Slack, Notion | 코드·소통·진행 기록 분리 |
| 대용량 환경 | Snowflake 검토 | 후반부 실제 데이터 제공 환경에 대비 |

도구는 확정안이 아니며 데이터 크기와 팀 숙련도를 확인한 뒤 결정한다.

## 7. 팀원 역할 배분 예시

역할은 완전히 분리하지 않고 **주 담당자와 검토자**를 함께 둔다.

| 팀원 | 주 역할 | 구체적인 업무 | 검토 업무 |
|---|---|---|---|
| 순성 | PM·데이터 통합 | 일정 관리, 대외 소통, DB·조인 구조, 진행 장애 관리 | 전체 산출물과 재현성 |
| 소이 | 초기 기획·브리핑 | 프로젝트 목표, 선정 이유, 발표 흐름, 멘토 제출 초안 | 16일까지 방향성과 메시지 검토 |
| 솔 | 데이터·문서 품질 | 컬럼·그레인 정의, 문서 검토, 근거 자료와 누락 사항 확인 | 회의록·최종 보고서 품질 |
| 현수 | 분석 설계 | 정상 기준선, 위험 지표, Z-score, 비교 모델 방향 설계 | 분석 논리와 모델 결과 |

### 소이 참여 종료 전 인수인계

- [ ] 프로젝트 목표와 선정 이유 확정
- [ ] 기획안 초안 작성
- [ ] 발표 스토리라인 구성
- [ ] 멘토 검토 의견 정리
- [ ] 수요일 종료 전 인수인계 문서 작성
- [ ] 이후 발표 담당자에게 발표 흐름 전달

### 업무 집중 방지 원칙

- 팀장은 일정과 통합을 담당하되 모든 문서를 직접 작성하지 않음
- 분석 설계를 현수 혼자 구현하지 않고 구현 담당자를 별도로 연결
- 솔은 단순 기록 담당이 아니라 데이터 정의와 품질 검토 책임을 가짐
- 중요 산출물은 작성자와 검토자를 다르게 배정

## 9. 프로젝트 목표 및 범위 1페이지 예시

### 목표

사용자 행동 로그를 바탕으로 정상 행동 기준선을 만들고 이상행동과 위험 사용자를 탐지한다.

### 사용자

기업 보안 담당자

### 해결할 문제

대량의 로그에서 우선 확인해야 할 사용자와 행동을 찾기 어렵다.

### 필수 기능

- 로그 통합
- 정상 기준선
- Z-score 이상 탐지
- 위험 점수
- 결과 시각화

### 선택 기능

- Isolation Forest 비교
- 공격 흐름 표현

### 제외 기능

- 실시간 탐지
- 자동 차단
- 운영 배포

### 성공 기준

- 동일한 코드로 결과를 재현할 수 있음
- 위험 점수 산출 근거를 설명할 수 있음
- 상위 위험 사용자의 행동을 로그로 확인할 수 있음

```text
│  ├─ scoring/
│  └─ visualization/
├─ notebooks/
├─ tests/

```

### 기본 규칙

- 원본 데이터는 GitHub에 올리지 않음
- `data/`, 대용량 결과물, 개인정보 파일은 `.gitignore` 처리
- 브랜치는 `feature/업무명` 형식 사용
- 커밋에는 변경 내용과 목적을 작성
- 중요한 변경은 다른 팀원 1명이 검토
- 분석 기준 변경은 코드뿐 아니라 결정 기록도 수정
