# SIEM 실시간 침해 조기탐지 및 공격경로 추적 시스템 개발 기획서

## 1. 프로젝트 개요

### 1.1 프로젝트명

**사용자·IP·자산 행동 기준선 기반 실시간 침해 조기탐지 및 공격경로 추적 시스템**

영문명 예시:

**Multi-Entity Behavioral Early Threat Detection & Attack Correlation System**

---

### 1.2 개발 기간 및 인력

| 구분 | 내용 |
|---|---|
| 개발 기간 | 3주 |

| 1일 작업시간 | 1인 7시간 |

## 2. 개발 배경

기업의 실제 보안 사고는 단일 이벤트만으로 명확하게 식별되지 않는 경우가 많습니다.

예를 들어 계정 탈취 공격에서는 다음과 같은 약한 이상징후가 연속적으로 발생할 수 있습니다.

```text
동일 IP 로그인 시도 급증
        ↓
다수 사용자 계정 접근
        ↓
로그인 실패율 증가
        ↓
일부 계정 로그인 성공
        ↓
신규 Source IP 확인
        ↓
기존에 접근하지 않던 Resource 접근
        ↓
DB Query 또는 데이터 조회량 증가
```

각 이벤트를 단독으로 보면 정상행동으로 해석될 가능성이 있지만, 시간순으로 연결하면 하나의 공격 흐름일 수 있습니다.

또한 실제 기업 환경에서는 다음과 같은 문제가 존재할 수 있습니다.

- 사용자가 많아 모든 로그를 사람이 직접 확인하기 어려움
- 동일한 Rule을 모든 사용자에게 적용하면 오탐이 증가함
- 정상 계정정보를 사용한 공격은 인증 성공 로그만으로 식별하기 어려움
- 침해 후 수일 또는 수개월 뒤 사후 분석 과정에서 공격이 확인될 수 있음
- 하나의 공격과 관련된 IP·계정·Host·Resource를 사람이 직접 연결해야 함
- Alert가 많아 실제 대응해야 할 사건의 우선순위 판단이 어려움

따라서 본 프로젝트는 단순한 이상치 탐지 모델이 아니라, **침해 징후를 가능한 한 빠르게 발견하고 관련 Entity를 연결하여 하나의 Incident로 구성하며, 보안담당자가 바로 조사할 수 있도록 탐지 근거와 위험도를 제공하는 시스템**을 목표로 합니다.

# 3. 개발 목적

본 프로젝트의 핵심 목적은 다음과 같습니다.

## 3.1 침해 조기탐지

기존의 사후 분석 중심 대응에서 벗어나, 로그가 발생하는 시점에 최대한 가깝게 이상행동을 탐지합니다.

목표 흐름:

```text
공격 시작
   ↓
이상신호 발생
   ↓
수분 단위 분석
   ↓
Risk Score 상승
   ↓
Incident 생성
   ↓
보안담당자 Alert
```

---

## 3.2 사용자별 획일적 Rule의 한계 보완

사용자마다 정상적인 행동패턴은 다를 수 있습니다.

예:

```text
사용자 A
평소 접속시간: 09:00~18:00

사용자 B
평소 접속시간: 18:00~03:00
```

따라서 단순히 `새벽 접속 = 위험`으로 판단하지 않고,

> "해당 사용자 자신의 평소 패턴에서 얼마나 벗어났는가?"

를 기준으로 판단하도록 설계합니다.

---

## 3.3 단일 로그가 아닌 복합 공격 흐름 탐지

다음처럼 여러 신호를 시간 순서로 연결합니다.

```text
Credential Stuffing
→ Login Success
→ Account Takeover 의심
→ New Resource Access
→ Data Access Surge
→ Exfiltration Risk
```

이를 통해 개별 Alert가 아니라 **Incident 단위로 사건을 관리**합니다.

---

## 3.4 관련 Entity 추적

공격 발생 시 다음 관계를 자동으로 연결합니다.

```text
Source IP
   ↓
User
   ↓
Host
   ↓
Resource / DB
```

이를 그래프 형태로 표현하여 조사 속도를 높이는 것을 목표로 합니다.

---

## 3.5 보안담당자 조사 우선순위 제공

모든 Alert를 동일하게 처리하지 않고,

- Dynamic Risk Score
- Attack Stage
- 관련 Entity 수
- 중요 자산 접근 여부
- 이상신호 개수

등을 결합해 위험도가 높은 Incident부터 확인할 수 있도록 합니다.

# 5. 프로젝트 성공 기준

본 프로젝트는 범용 보안제품 완성을 목표로 하지 않습니다.

3주 내 완성해야 하는 **기업 적용형 PoC의 성공 기준**은 다음과 같습니다.

### 필수 완료 기준

1. 실제 또는 동일 Schema의 보안 로그를 입력할 수 있다.
2. 로그를 공통 Event Schema로 정규화할 수 있다.
3. User/IP/Resource 기준선을 생성할 수 있다.
4. 최소 6개의 핵심 이상신호를 탐지할 수 있다.
5. 통계 기반 이상도 및 ML Anomaly Score를 계산할 수 있다.
6. 관련 이벤트를 하나의 Incident로 묶을 수 있다.
7. 공격 진행단계를 추정할 수 있다.
8. Risk Score가 이벤트에 따라 동적으로 변경된다.
9. 관련 IP/User/Host/Resource 관계를 추적할 수 있다.
10. 보안담당자가 확인 가능한 Dashboard를 제공한다.
11. 탐지 이유(Evidence)를 출력한다.
12. 대응 권고(Recommended Action)를 출력한다.
13. 정상/공격 테스트 시나리오로 성능을 검증한다.
14. MTTD, Recall, Precision, FPR 등의 지표를 산출한다.
15. 최초 입력부터 최종 Incident 출력까지 End-to-End 실행 가능하다.

# 10. Anomaly Detection 설계

## 10.1 통계 기반 탐지

- Z-score
- 비율 변화
- Historical Set 비교
- Percentile
- Rolling Window 집계

예:

```text
평균 실패율 5%
현재 실패율 91%

→ Failure Rate Anomaly
```

---

## 10.2 Isolation Forest

Isolation Forest는 프로젝트의 단독 핵심모델이 아니라 **Rule/통계 탐지를 보완하는 비지도 이상탐지 모델**로 사용합니다.

입력 Feature 예시:

- `login_count`
- `login_fail_count`
- `failure_rate`
- `unique_user_count`
- `unique_host_count`
- `new_ip_count`
- `new_resource_count`
- `query_count`
- `bytes_out`

출력:

```text
ML Anomaly Score
0~100
```

# 11. Event Correlation 설계

단일 Alert를 그대로 Incident로 만들지 않습니다.

다음 정보를 기반으로 연결합니다.

- 동일 `user_id`
- 동일 `src_ip`
- 동일 `session_id`
- 동일 `host_id`
- 일정 Time Window
- 이벤트 순서

예:

```text
10:00 LOGIN_FAIL
10:01 LOGIN_FAIL
10:02 LOGIN_FAIL
10:04 LOGIN_SUCCESS
10:08 NEW_RESOURCE
10:12 DB_QUERY_SPIKE
```

결과:

```text
Incident #001

Credential Attack
→ Account Takeover
→ Post-Compromise
```

# 12. Attack Stage

| Stage | 이름 | 대표 이벤트 |
|---:|---|---|
| 1 | Credential Attack | 로그인 급증, 다수 계정, 실패율 급증 |
| 2 | Account Takeover | 로그인 성공, 신규 IP |
| 3 | Post-Compromise | 신규 Host/Resource, 권한 행동 |
| 4 | Exfiltration Risk | Query·다운로드·Outbound 증가 |

공격 진행에 따라 Incident 상태를 갱신합니다.

# 13. Dynamic Risk Score

초기 PoC에서는 Heuristic Weight를 사용합니다.

예:

```text
Risk Score =
0.30 × Signal Score
+ 0.20 × ML Anomaly Score
+ 0.30 × Sequence Score
+ 0.20 × Context Score
```

가중치는 확정값이 아니며 실제 로그 및 검증 결과를 기반으로 조정합니다.

### 예시

```text
10:03
Failure Rate Spike
Risk 35

10:06
Multi Account Access
Risk 54

10:09
Login Success from New IP
Risk 72

10:14
New DB Access
Risk 85

10:18
Query Spike
Risk 94
```

# 16. 성능평가 계획

## 16.1 핵심 KPI

| KPI | 설명 |
|---|---|
| MTTD | 공격 시작 → 최초 탐지 시간 |
| Recall | 실제 공격 중 탐지 비율 |
| Precision | 탐지 Alert 중 실제 공격 비율 |
| FPR | 정상 행동을 공격으로 판단한 비율 |
| Correlation Accuracy | 관련 이벤트를 동일 사건으로 묶은 정확도 |
| Attack Stage Accuracy | 공격 단계 식별 성능 |
| Trace Coverage | 관련 IP/User/Host/Resource 연결 범위 |
| Explainability Coverage | 탐지에 대한 근거 제공 비율 |

---

## 16.2 비교실험

가능하면 다음 모델을 비교합니다.

### Baseline A

```text
Rule Only
```

### Baseline B

```text
Baseline + Statistical Anomaly
```

### Proposed

```text
Rule
+ Multi-Entity Baseline
+ Statistical Anomaly
+ Isolation Forest
+ Event Correlation
+ Dynamic Risk
```

목표는 단순 Accuracy 최대화가 아니라,

```text

False Positive 감소

```

여부를 확인하는 것입니다.

# 30. 프로젝트 핵심 정의

본 프로젝트는 단순히 이상 로그를 분류하는 모델이 아닙니다.

> **사용자·IP·자산의 평소 행동을 기준선으로 만들고, 실시간에 가까운 보안 로그에서 이상신호를 탐지하며, 서로 연관된 이벤트를 하나의 공격 Incident로 연결하고, 공격 진행단계와 위험도를 동적으로 갱신하여 관련 IP·사용자·Host·Resource의 공격경로와 대응근거를 보안담당자에게 제공하는 기업 적용형 침해 조기탐지 PoC**

를 개발하는 것이 최종 목표입니다.
