# 파일명 및 GitHub 폴더 관리 규칙

## 1. 목적

이 규칙은 팀원이 파일의 내용과 위치를 빠르게 이해하고, 중복 파일과 불필요한 폴더 증가를 막기 위한 기준이다.

핵심 원칙은 다음 세 가지다.

1. 폴더는 **자료의 종류**에 따라 한글로 구분한다.
2. 폴더명과 파일명은 **한글을 기본으로 짧고 일관되게** 작성한다.
3. 작업 원본의 변경 이력은 **Git 기록**으로 관리하고, 검토·승인·제출 시점의 산출물은 **날짜와 버전이 포함된 파일명**으로 식별한다.

## 2. 권장 폴더 구조

```text
project-root/
├─ README.md              # 프로젝트 소개, 실행법, 담당자
├─ 문서/                  # 기획서, 회의록, 조사·설계 문서
│  ├─ 기획/               # 목표, 요구사항, 일정
│  ├─ 회의록/             # 회의록
│  └─ 자료조사/           # 논문·서비스 조사, 참고 문서
├─ 데이터/                # 분석 데이터
│  ├─ 원본/               # 원본 데이터: 수정 금지
│  └─ 가공/               # 정제·변환된 데이터
├─ 분석노트/              # 탐색 및 분석 노트북
├─ 코드/                  # 재사용 가능한 코드
├─ 산출물/                # 표, 그림, 보고서, 발표자료
├─ 테스트/                # 테스트 코드가 있을 때만 생성
├─ .gitignore
└─ requirements.txt       # Python 사용 시
```

### 폴더 운영 원칙

- 기본 폴더는 `문서`, `데이터`, `분석노트`, `코드`, `산출물` 다섯 개만 사용한다.
- 팀이 직접 만드는 폴더명과 파일명은 한글을 기본으로 작성한다.
- 영문 약어가 널리 통용되는 경우에도 가능한 한 한글 설명과 함께 사용한다. 예: `보안정보이벤트관리_SIEM_구축계획.md`.
- `tests` 등 선택 폴더는 실제 파일이 생길 때 만든다. 빈 폴더를 미리 만들지 않는다.
- 폴더 깊이는 루트 기준 **최대 3단계**를 권장한다.
- 연도·월 폴더는 만들지 않는다. 날짜는 필요한 파일명과 Git 기록으로 확인한다.
- `최종`, `진짜최종`, `최종수정`, `이전버전`, `백업` 폴더를 만들지 않는다.
- 같은 문서를 여러 위치에 복사하지 않는다. 원본 한 개만 두고 README에서 링크한다.
- 외부에서 받은 파일은 `데이터/원본/` 또는 `문서/자료조사/` 중 성격에 맞는 한 곳에 둔다.
- 실행 결과는 모두 `산출물/`에 저장하고, 코드·분석노트 폴더에 섞지 않는다.

## 3. 파일명 규칙

### 3.1 기본 형식

```text
[문서번호_]주제_내용[_YYYYMMDD][_vNN][_상태].확장자
```

- 대괄호(`[]`) 안의 항목은 필요한 경우에만 사용한다.
- `주제`와 `내용`은 파일을 열지 않아도 용도를 알 수 있도록 작성한다.
- 폴더명과 파일명의 주제·내용은 한글로 작성한다.
- 단어 구분은 언더스코어(`_`)를 사용한다.
- 공백, 괄호, 특수문자, 이모지는 사용하지 않는다.
- 제품명, 기술명, 확장자 등 고유명사를 제외하고 영문 단어를 사용하지 않는다.
- 문서번호는 `01`, `02`, `03-1`, `03-2`처럼 작성하며, 제출 묶음이나 순서가 있는 문서에 사용한다.
- 날짜는 해당 버전을 확정하거나 공유한 날짜를 `YYYYMMDD` 8자리로 작성한다.
- 버전은 반드시 소문자 `v`와 두 자리 숫자를 결합해 `v01`, `v02`처럼 작성한다.
- 상태는 승인된 용어인 `작업본`, `검토본`, `현행본`, `제출본` 중 하나만 사용한다.
- 파일명은 확장자를 포함해 가능하면 60자 이내로 유지한다.

### 3.2 파일 단계별 형식

| 단계 | 형식 | 예시 |
|---|---|---|
| 상시 수정하는 작업 원본 | `주제_내용.확장자` | `위험점수_산정기준.md` |
| 순서가 있는 작업 문서 | `NN_주제_내용.확장자` | `02_분석설계_데이터정의.md` |
| 팀 검토용 고정본 | `NN_주제_내용_YYYYMMDD_vNN_검토본.확장자` | `02_분석설계_20260921_v01_검토본.pdf` |
| 현재 승인된 기준 문서 | `NN_주제_내용_YYYYMMDD_vNN_현행본.확장자` | `04_위험점수_산정기준_20260922_v02_현행본.pdf` |
| 외부 제출 파일 | `NN_주제_내용_팀명_YYYYMMDD_vNN_제출본.확장자` | `07-1_최종발표자료_2팀_20260928_v01_제출본.pptx` |
| 제출 묶음 폴더 | `제출_산출물_팀명_YYYYMMDD_vNN` | `제출_산출물_2팀_20260928_v01` |

### 3.3 상태명 정의

| 상태 | 의미 | 사용 기준 |
|---|---|---|
| `작업본` | 작성 중인 공유용 사본 | Git 밖에서 중간 파일을 공유해야 할 때만 사용 |
| `검토본` | 리뷰를 요청한 고정본 | 내용과 버전을 고정해 검토자에게 전달할 때 사용 |
| `현행본` | 내부 승인이 끝난 현재 기준본 | 같은 문서에서 한 개만 유지 |
| `제출본` | 외부 기관·멘토 등에 실제 제출한 파일 | 제출 후 내용을 변경하지 않음 |

`최종`, `진짜최종`, `최종수정`, `완성본`, `수정본`은 상태명으로 사용하지 않는다.

### 3.4 파일 유형별 기준

| 유형 | 규칙 | 예시 |
|---|---|---|
| 코드 | 한글 기능명 | `위험점수_계산.py` |
| 노트북 | 순서 2자리 + 한글 분석명 | `01_데이터_점검.ipynb` |
| 데이터 | 한글 자료명 + 처리 단계 | `보안로그_원본.csv`, `보안로그_정제.csv` |
| 일반 문서 | 한글 주제 + 내용 | `위험점수_산정기준.md` |
| 회의록 | `회의록_YYYYMMDD_주제` | `회의록_20260914_착수회의.md` |
| 검토 산출물 | `NN_주제_YYYYMMDD_vNN_검토본` | `05_분석보고서_20260923_v02_검토본.pdf` |
| 제출 산출물 | `NN_주제_팀명_YYYYMMDD_vNN_제출본` | `07-1_최종발표자료_2팀_20260928_v01_제출본.pptx` |
| 이미지·차트 | 번호 + 한글 지표·내용 | `01_일별_경보건수.png` |

### 3.5 영문 파일명 허용 예외

다음 파일은 도구와 플랫폼의 자동 인식 또는 실행 호환성을 위해 표준 영문 이름을 유지할 수 있다.

- GitHub 표준 파일: `README.md`, `LICENSE`, `.gitignore`, `CONTRIBUTING.md`
- 개발 도구 설정 파일: `requirements.txt`, `package.json`, `pyproject.toml`, `Dockerfile`
- 프레임워크가 이름을 지정하는 파일: `__init__.py`, `index.html` 등
- 외부 시스템 연동 규격에서 영문 파일명을 요구하는 경우

예외 파일을 제외한 팀 작성 자료와 산출물에는 한글 이름을 사용한다.

### 3.6 날짜와 버전 사용 기준

- 코드, 노트북, 상시 갱신 문서에는 날짜와 버전을 붙이지 않는다. 변경 이력은 Git으로 관리한다.
- 검토본, 현행본, 제출본처럼 특정 시점을 고정해야 하는 파일에는 날짜와 버전을 함께 붙인다.
- 작업 중인 같은 파일을 수정할 때마다 `v01`, `v02`로 복제하지 않는다.
- 검토 요청, 내부 승인 또는 외부 재제출처럼 공식 기준점이 바뀔 때만 버전을 올린다.
- 같은 버전에서 파일 형식만 다른 경우 버전 번호를 동일하게 유지한다. 예: `.pptx`와 `.pdf`가 같은 내용이면 모두 `v02`.
- 날짜만 바꾸고 버전을 그대로 두거나, 버전만 바꾸고 변경 내용을 기록하지 않는 방식은 금지한다.

### 3.7 좋은 예와 피해야 할 예

| 피해야 할 이름 | 권장 이름 |
|---|---|
| `SIEM_보고서_진짜최종_수정2.pdf` | `05_위험분석보고서_20260928_v03_제출본.pdf` |
| `분석 결과 9월 14일.csv` | `경보분석_20260914.csv` |
| `프로젝트회의록최종본(팀장수정).docx` | `회의록_20260914_착수회의.md` |
| `위험점수분석_v1_최종_현행본.ipynb` | `03_위험점수_분석.ipynb` |

## 4. 버전관리 규칙

### 4.1 관리 원칙

1. 편집 가능한 작업 원본은 한 개만 유지하고 Git 커밋으로 변경 이력을 남긴다.
2. `vNN` 파일은 공식 검토·승인·제출 시점을 보존하는 스냅샷으로만 만든다.
3. 파일명 버전과 Git 커밋은 서로 보완한다. 파일명만 바꾸고 내용 변경을 커밋하지 않는 방식은 사용하지 않는다.
4. `현행본`은 문서별 한 개만 유지한다. 새 현행본이 승인되면 이전 현행본은 Git 이력 또는 공식 제출 기록으로 조회한다.
5. `제출본`은 제출 후 수정하지 않는다. 수정이 필요하면 새 버전으로 저장하고 재제출 사유를 기록한다.

### 4.2 버전 번호 부여

- 최초 공식 검토본 또는 제출본은 `v01`로 시작한다.
- 검토 의견 반영, 산식 변경, 수치 수정, 화면 교체처럼 내용이 바뀌면 `v02`, `v03` 순서로 1씩 올린다.
- 오탈자처럼 의미가 바뀌지 않는 수정도 이미 공유하거나 제출한 파일이라면 새 버전으로 만든다.
- 파일을 단순히 PDF로 변환하거나 압축한 경우 내용이 같다면 버전을 올리지 않는다.
- 버전 번호를 건너뛰거나 `v1`, `ver2`, `rev03`처럼 다른 표기를 섞지 않는다.

### 4.3 상태 전환

```text
작업 원본
→ v01_검토본
→ 피드백 반영
→ v02_검토본
→ v02_현행본
→ v02_제출본
```

- 검토 중 내용이 바뀌면 작업 원본에 먼저 반영하고 새 검토본을 생성한다.
- 동일한 내용이 승인·제출되는 경우 버전은 유지하고 상태만 `현행본` 또는 `제출본`으로 변경한다.
- 제출 후 수정 요청을 받으면 작업 원본을 수정한 뒤 다음 버전의 검토본부터 다시 시작한다.

### 4.4 제출 묶음 관리

외부 제출 시에는 다음 형식의 폴더 한 개에 제출 파일을 모은다.

```text
제출_산출물_팀명_YYYYMMDD_vNN/
├─ 01_프로젝트기획서_팀명_YYYYMMDD_vNN_제출본.pdf
├─ 02_분석설계서_팀명_YYYYMMDD_vNN_제출본.pdf
├─ 03-1_분석결과_팀명_YYYYMMDD_vNN_제출본.pdf
├─ 07-1_최종발표자료_팀명_YYYYMMDD_vNN_제출본.pptx
├─ 07-2_발표자료_팀명_YYYYMMDD_vNN_제출본.pdf
├─ README_먼저읽기.md
└─ 파일목록_SHA256.csv
```

- 제출 묶음 안의 문서번호는 발표·검토 순서를 따른다.
- 묶음 버전과 내부 파일 버전은 원칙적으로 동일하게 맞춘다.
- `README_먼저읽기.md`에는 제출 목적, 제출일, 작성자, 파일 목록, 실행 방법을 기록한다.
- `파일목록_SHA256.csv`는 공식 제출 파일의 무결성 확인이 필요할 때 생성한다.
- 제출 묶음을 수정해야 하면 기존 폴더를 덮어쓰지 않고 다음 버전의 새 폴더를 만든다.

### 4.5 버전 변경 기록

공식 산출물에는 `문서/관리/산출물_버전기록.md` 또는 제출 묶음의 `README_먼저읽기.md`에 다음 내용을 기록한다.

| 항목 | 내용 |
|---|---|
| 버전 | `v01`, `v02` 등 |
| 확정일 | `YYYY-MM-DD` |
| 상태 | 검토본 / 현행본 / 제출본 |
| 작성자 | 변경 담당자 |
| 검토자 | 검토 또는 승인 담당자 |
| 변경 내용 | 이전 버전과 달라진 핵심 사항 |
| 관련 커밋 | Git 커밋 해시 또는 Pull Request 링크 |

### 4.6 기존 파일 적용 기준

- 이 규칙은 개정 이후 새로 생성하거나 내용이 갱신되는 파일부터 적용한다.
- 기존 파일을 규칙 적용만을 목적으로 한 번에 모두 개명하지 않는다.
- 기존 파일을 수정할 때 새 규칙에 맞춰 이름을 정리하고, Git에서 이동 이력을 남긴다.

## 5. GitHub 관리 규칙

### 브랜치

- `main`: 검토가 끝난 안정 버전만 유지한다.
- 작업 브랜치: `종류/짧은-설명` 형식을 사용한다.

```text
feature/risk-scoring
fix/data-loading
docs/folder-rules
analysis/alert-patterns
```

- 종류는 `feature`, `fix`, `docs`, `analysis`, `refactor` 중에서 선택한다.
- 한 브랜치에는 하나의 작업 목적만 담는다.
- 병합이 끝난 브랜치는 삭제한다.

### 커밋

커밋 메시지는 다음 형식을 사용한다.

```text
종류: 변경 내용
```

예시:

```text
docs: 파일명 및 폴더 관리 규칙 추가
data: 보안 로그 결측치 정제
analysis: 위험 점수 분포 분석 추가
fix: 날짜 변환 오류 수정
```

- 종류는 `docs`, `data`, `analysis`, `feat`, `fix`, `refactor`, `test`, `chore`를 사용한다.
- 커밋 하나에는 한 가지 목적의 변경만 포함한다.
- `수정`, `업데이트`, `작업중`처럼 내용이 불분명한 메시지는 피한다.

### Pull Request

- `main`에 직접 작업하지 않고 작업 브랜치에서 Pull Request를 만든다.
- 제목은 커밋 메시지와 같은 형식으로 작성한다.
- 본문에는 `변경 목적`, `주요 변경`, `확인 방법`을 적는다.
- 대용량 파일, 개인정보, 비밀키가 포함되지 않았는지 확인한 후 병합한다.
- 최소 1명의 확인을 받은 뒤 병합하는 것을 원칙으로 한다.

## 6. Git에 올리지 않는 파일

다음 항목은 `.gitignore`에 등록한다.

```gitignore
# 환경 및 비밀정보
.env
.env.*
*.key
*.pem

# Python
__pycache__/
*.py[cod]
.venv/

# Jupyter
.ipynb_checkpoints/

# OS 및 편집기
.DS_Store
Thumbs.db
.vscode/

# 로컬 임시파일
tmp/
temp/
*.log

# 민감하거나 큰 원본 데이터
데이터/원본/*
!데이터/원본/README.md
```

- 개인정보와 인증정보는 크기와 관계없이 커밋하지 않는다.
- 대용량 데이터는 공유 스토리지에 보관하고 `데이터/원본/README.md`에 위치와 취득 방법을 기록한다.
- GitHub의 일반 파일 한도를 피하기 위한 ZIP 분할 저장은 하지 않는다.
- 결과를 코드로 재생성할 수 있으면 중간 산출물은 커밋하지 않는다.

## 7. README 필수 항목

루트 `README.md`에는 최소한 다음 내용을 둔다.

1. 프로젝트 목적
2. 폴더 구조
3. 실행 방법
4. 데이터 출처와 사용 제한
5. 주요 산출물 링크
6. 팀원과 역할

세부 폴더의 README는 별도 설명 없이는 이해하기 어려운 폴더에만 만든다.

## 8. 팀 점검 체크리스트

커밋 또는 Pull Request 전에 다음을 확인한다.

- [ ] 파일이 정해진 폴더에 있는가?
- [ ] 파일명만 보고 내용을 짐작할 수 있는가?
- [ ] 검토·현행·제출 파일의 날짜, 버전, 승인된 상태명이 규칙과 일치하는가?
- [ ] `최종`, `진짜최종`, `수정본`, `완성본` 같은 비승인 상태명이 없는가?
- [ ] 같은 문서의 `현행본`이 두 개 이상 존재하지 않는가?
- [ ] 공식 산출물의 변경 내용과 관련 Git 커밋이 기록되었는가?
- [ ] 같은 파일의 복사본이 여러 폴더에 없는가?
- [ ] 개인정보, 비밀키, 대용량 원본 데이터가 제외되었는가?
- [ ] 생성 결과와 원본 데이터가 코드·문서 폴더에 섞이지 않았는가?
- [ ] README 또는 관련 문서 링크가 최신인가?
