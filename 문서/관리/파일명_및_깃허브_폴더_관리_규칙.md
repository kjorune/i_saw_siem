# 파일명 및 GitHub 폴더 관리 규칙

## 1. 목적

이 규칙은 팀원이 파일의 내용과 위치를 빠르게 이해하고, 중복 파일과 불필요한 폴더 증가를 막기 위한 기준이다.

핵심 원칙은 다음 세 가지다.

1. 폴더는 **자료의 종류**에 따라 한글로 구분한다.
2. 폴더명과 파일명은 **한글을 기본으로 짧고 일관되게** 작성한다.
3. 버전 이력은 파일 복사보다 **Git 기록**으로 관리한다.

## 2. 권장 폴더 구조

```text
project-root/
├─ README.md              # 프로젝트 소개, 실행법, 담당자
├─ 문서/                  # 기획서, 회의록, 조사·설계 문서
│  ├─ 기획/               # 목표, 요구사항, 일정
│  ├─ 회의록/             # 회의록
│  └─ 자료조사/           # 논문·서비스 조사, 참고 문서
├─ 데이터/                # 분석 데이터
│  ├─ 원본/               # 원본 데이터: 수정 금지
│  └─ 가공/               # 정제·변환된 데이터
├─ 분석노트/              # 탐색 및 분석 노트북
├─ 코드/                  # 재사용 가능한 코드
├─ 산출물/                # 표, 그림, 보고서, 발표자료
├─ 테스트/                # 테스트 코드가 있을 때만 생성
├─ .gitignore
└─ requirements.txt       # Python 사용 시
```

### 폴더 운영 원칙

- 기본 폴더는 `문서`, `데이터`, `분석노트`, `코드`, `산출물` 다섯 개만 사용한다.
- 팀이 직접 만드는 폴더명과 파일명은 한글을 기본으로 작성한다.
- 영문 약어가 널리 통용되는 경우에도 가능한 한 한글 설명과 함께 사용한다. 예: `보안정보이벤트관리_SIEM_구축계획.md`.
- `tests` 등 선택 폴더는 실제 파일이 생길 때 만든다. 빈 폴더를 미리 만들지 않는다.
- 폴더 깊이는 루트 기준 **최대 3단계**를 권장한다.
- 연도·월 폴더는 만들지 않는다. 날짜는 필요한 파일명과 Git 기록으로 확인한다.
- `최종`, `진짜최종`, `최종수정`, `이전버전`, `백업` 폴더를 만들지 않는다.
- 같은 문서를 여러 위치에 복사하지 않는다. 원본 한 개만 두고 README에서 링크한다.
- 외부에서 받은 파일은 `데이터/원본/` 또는 `문서/자료조사/` 중 성격에 맞는 한 곳에 둔다.
- 실행 결과는 모두 `산출물/`에 저장하고, 코드·분석노트 폴더에 섞지 않는다.

## 3. 파일명 규칙

### 공통 형식

```text
주제_내용[_YYYYMMDD][_vNN].확장자
```

- `주제`와 `내용`은 파일을 열지 않아도 용도를 알 수 있게 작성한다.
- 폴더명과 파일명의 주제·내용은 한글로 작성한다.
- 단어 구분은 언더스코어(`_`)를 사용한다.
- 공백, 괄호, 특수문자, 이모지는 사용하지 않는다.
- 제품명, 기술명, 확장자 등 고유명사를 제외하고 영문 단어를 사용하지 않는다.
- 날짜가 필요하면 `YYYYMMDD` 8자리 형식을 사용한다.
- 버전이 필요하면 `v01`, `v02`처럼 두 자리로 작성한다.
- 파일명은 확장자를 포함해 가능하면 60자 이내로 유지한다.

### 파일 유형별 기준

| 유형 | 규칙 | 예시 |
|---|---|---|
| 코드 | 한글 기능명 | `위험점수_계산.py` |
| 노트북 | 순서 2자리 + 한글 분석명 | `01_데이터_점검.ipynb` |
| 데이터 | 한글 자료명 + 처리 단계 | `보안로그_원본.csv`, `보안로그_정제.csv` |
| 일반 문서 | 한글 주제 + 내용 | `위험점수_산정기준.md` |
| 회의록 | `회의록_YYYYMMDD_주제` | `회의록_20260914_착수회의.md` |
| 배포 산출물 | `주제_YYYYMMDD_vNN` | `siem_분석보고서_20260914_v01.pdf` |
| 이미지·차트 | 번호 + 한글 지표·내용 | `01_일별_경보건수.png` |

### 영문 파일명 허용 예외

다음 파일은 도구와 플랫폼의 자동 인식 또는 실행 호환성을 위해 표준 영문 이름을 유지할 수 있다.

- GitHub 표준 파일: `README.md`, `LICENSE`, `.gitignore`, `CONTRIBUTING.md`
- 개발 도구 설정 파일: `requirements.txt`, `package.json`, `pyproject.toml`, `Dockerfile`
- 프레임워크가 이름을 지정하는 파일: `__init__.py`, `index.html` 등
- 외부 시스템 연동 규격에서 영문 파일명을 요구하는 경우

예외 파일을 제외한 팀 작성 자료와 산출물에는 한글 이름을 사용한다.

### 날짜와 버전 사용 기준

- 코드, 노트북, 상시 갱신 문서에는 날짜와 버전을 붙이지 않는다. 변경 이력은 Git으로 관리한다.
- 외부 제출물, 배포 파일, 회의록처럼 특정 시점 식별이 필요한 파일에만 날짜를 붙인다.
- 작업 중인 같은 파일을 `v01`, `v02`로 계속 복제하지 않는다.
- 외부 제출본을 구분해야 할 때만 버전을 올린다.
- `최종`, `현행본`, `수정본`, `완성본` 같은 상태 표현은 파일명에 넣지 않는다.

### 좋은 예와 피해야 할 예

| 피해야 할 이름 | 권장 이름 |
|---|---|
| `SIEM_보고서_진짜최종_수정2.md` | `siem_분석보고서.md` |
| `분석 결과 9월 14일.csv` | `경보분석_20260914.csv` |
| `프로젝트회의록최종본(팀장수정).docx` | `회의록_20260914_착수회의.docx` |
| `위험점수분석_v1_최종_현행본.ipynb` | `03_위험점수_분석.ipynb` |

## 4. GitHub 관리 규칙

### 브랜치

- `main`: 검토가 끝난 안정 버전만 유지한다.
- 작업 브랜치: `종류/짧은-설명` 형식을 사용한다.

```text
feature/risk-scoring
fix/data-loading
docs/folder-rules
analysis/alert-patterns
```

- 종류는 `feature`, `fix`, `docs`, `analysis`, `refactor` 중에서 선택한다.
- 한 브랜치에는 하나의 작업 목적만 담는다.
- 병합이 끝난 브랜치는 삭제한다.

### 커밋

커밋 메시지는 다음 형식을 사용한다.

```text
종류: 변경 내용
```

예시:

```text
docs: 파일명 및 폴더 관리 규칙 추가
data: 보안 로그 결측치 정제
analysis: 위험 점수 분포 분석 추가
fix: 날짜 변환 오류 수정
```

- 종류는 `docs`, `data`, `analysis`, `feat`, `fix`, `refactor`, `test`, `chore`를 사용한다.
- 커밋 하나에는 한 가지 목적의 변경만 포함한다.
- `수정`, `업데이트`, `작업중`처럼 내용이 불분명한 메시지는 피한다.

### Pull Request

- `main`에 직접 작업하지 않고 작업 브랜치에서 Pull Request를 만든다.
- 제목은 커밋 메시지와 같은 형식으로 작성한다.
- 본문에는 `변경 목적`, `주요 변경`, `확인 방법`을 적는다.
- 대용량 파일, 개인정보, 비밀키가 포함되지 않았는지 확인한 후 병합한다.
- 최소 1명의 확인을 받은 뒤 병합하는 것을 원칙으로 한다.

## 5. Git에 올리지 않는 파일

다음 항목은 `.gitignore`에 등록한다.

```gitignore
# 환경 및 비밀정보
.env
.env.*
*.key
*.pem

# Python
__pycache__/
*.py[cod]
.venv/

# Jupyter
.ipynb_checkpoints/

# OS 및 편집기
.DS_Store
Thumbs.db
.vscode/

# 로컬 임시파일
tmp/
temp/
*.log

# 민감하거나 큰 원본 데이터
데이터/원본/*
!데이터/원본/README.md
```

- 개인정보와 인증정보는 크기와 관계없이 커밋하지 않는다.
- 대용량 데이터는 공유 스토리지에 보관하고 `데이터/원본/README.md`에 위치와 취득 방법을 기록한다.
- GitHub의 일반 파일 한도를 피하기 위한 ZIP 분할 저장은 하지 않는다.
- 결과를 코드로 재생성할 수 있으면 중간 산출물은 커밋하지 않는다.

## 6. README 필수 항목

루트 `README.md`에는 최소한 다음 내용을 둔다.

1. 프로젝트 목적
2. 폴더 구조
3. 실행 방법
4. 데이터 출처와 사용 제한
5. 주요 산출물 링크
6. 팀원과 역할

세부 폴더의 README는 별도 설명 없이는 이해하기 어려운 폴더에만 만든다.

## 7. 팀 점검 체크리스트

커밋 또는 Pull Request 전에 다음을 확인한다.

- [ ] 파일이 정해진 폴더에 있는가?
- [ ] 파일명만 보고 내용을 짐작할 수 있는가?
- [ ] `최종`, `수정본`, `현행본` 같은 표현이 없는가?
- [ ] 같은 파일의 복사본이 여러 폴더에 없는가?
- [ ] 개인정보, 비밀키, 대용량 원본 데이터가 제외되었는가?
- [ ] 생성 결과와 원본 데이터가 코드·문서 폴더에 섞이지 않았는가?
- [ ] README 또는 관련 문서 링크가 최신인가?

## 8. 적용 예시

```text
보안프로젝트/
├─ README.md
├─ 문서/
│  ├─ 기획/
│  │  └─ 프로젝트_계획.md
│  ├─ 회의록/
│  │  └─ 회의록_20260914_착수회의.md
│  └─ 자료조사/
│     └─ 위험점수_논문조사.md
├─ 데이터/
│  ├─ 원본/
│  │  └─ README.md
│  └─ 가공/
│     └─ 보안로그_정제.csv
├─ 분석노트/
│  ├─ 01_데이터_점검.ipynb
│  └─ 02_위험점수_분석.ipynb
├─ 코드/
│  ├─ 데이터_전처리.py
│  └─ 위험점수_계산.py
├─ 산출물/
│  ├─ 01_위험점수_분포.png
│  └─ siem_분석보고서_20260914_v01.pdf
├─ .gitignore
└─ requirements.txt
```

이 구조를 기본값으로 사용하되, 새 폴더가 꼭 필요한 경우 팀 합의 후 추가한다.
