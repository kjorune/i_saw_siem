- 목표: 프로젝트 주제, 개발 범위, 데이터 요청 및 탐지 방법의 방향 정리

## 2. 안건별 논의

### 안건 1. 일정과 개발 범위

- 1주 차에 핵심 기능을 구현하고, 2주 차에는 실무자 피드백과 성능 검증, 3주 차에는 보완·문서화·발표를 진행하는 안을 논의함.
- 기능을 많이 추가하기보다 기업에서 사용할 수 있는 최소 기능을 완성도 있게 구현하기로 함.
- 최종 범위는 기업이 제공하는 데이터의 종류·규모·전달 방식과 개발 난도를 확인한 뒤 확정함.

### 안건 2. 분석 주제와 결과물

- 로그인 실패, 비정상 접속, 파일 접근·반출 등 개별 이상 지표와 로그인부터 자원 접근까지 이어지는 공격 흐름을 함께 분석함.
- 로그인 전·후 행동을 구분하고 사용자 또는 사건 단위로 위험 점수를 산출하는 방향을 검토함.
- 계정·IP·호스트·접근 자원의 관계를 연결해 의심 계정과 침입 경로를 빠르게 확인할 수 있도록 함.
- 실제 공격 근원지를 완전히 추적하기보다 조사 대상과 연결 자원을 제시하는 수준으로 범위를 제한함.
- 실제 보안 사고 사례와 기존 연구를 주제 및 분석 구조의 근거로 활용함.

### 안건 3. 위험 점수와 성능평가

- 로그인 실패 횟수, 다운로드 수, 접속 시간 등의 파생변수를 이상 지표로 사용함.
- 지표 기준과 가중치는 논문, 기업 담당자 및 외부 보안 실무자의 의견을 근거로 정함.
- 설명 가능한 Z-score를 기본 탐지 방식으로, Isolation Forest를 종합 패턴 비교용 보조 모델로 검토함.
- 실시간 분석에 적합한 RCF는 향후 기업 적용을 위한 고도화 범위로 둠.
- 성능평가를 위해 정상·이상 라벨과 Y값이 필요하며, 라벨이 없다면 정답 세트 생성 방식을 설계해야 함.
- 정탐·오탐·미탐 등의 지표와 실무자 인터뷰·설문을 통해 기술 성능과 현업 활용성을 함께 평가함.

### 안건 4. 데이터 확보와 처리

- 기업에 필요한 컬럼과 권장 형식을 정리해 요청하되, 보안상 제공이 어려운 항목은 실제 수령 범위에 맞춰 조정함.
- CSV·JSON 파일 제공인지 OpenSearch API 방식인지 확인함. API 방식이면 인증, 호출 제한, 쿼리 및 수집 구현 시간이 추가됨.
- 대용량 데이터에는 ETL, 캐싱, 분할 처리를 고려하고 Pandas보다 빠른 Polars를 검토함.
- Spark와 OpenSearch 연동은 난도가 높으므로 데이터 규모와 기업 요구가 확인된 후 적용 여부를 결정함.

### 안건 5. 시스템 구조와 협업

- 데이터를 받은 뒤 사용자, VPN, 서버, 보안 시스템, 로그 저장소의 관계와 예상 침입 경로를 토폴로지로 작성함.
- 팀이 먼저 데이터를 분석해 판단 기준을 정한 뒤 AI에 분류·탐지 업무를 분담함.
- 개발 문서와 자료는 GitHub에 모으고, 공통 용어는 별도 문서로 정리함.
- 회의록은 순번제로 작성하며, 회의 시작·종료 시 참석자와 시간이 보이는 증빙을 남김.
